## 部署过程与最终结果

1. 首次命令行部署返回 `EISDIR`。将函数内模块整理为平铺文件，并重新通过 139 项检查和 Node.js 16.13.1 业务冒烟。
2. 随后完整部署返回 `getCloudAPISignedHeader failed`，云端响应 `base_resp.ret=41002`、`errmsg=system error.`。重试后仍失败。
3. 袁嘉亮确认已退出并重新扫码登录，之后再次完整部署，仍为相同错误。
4. 尝试工具公开的整目录增量更新（依赖未变），也被相同签名请求错误拒绝。没有将该命令的进程退出码 0 当成部署成功。
5. 在手动上传前，通过新版本地项目的微信模拟器真实调用 whoami，返回 `ok:true`、`environmentId=cloud1-d6gvp9cql29a1164e`、`stage=p2-room-foundation`，证实当时尚未更新。未公开账号标识。
6. 袁嘉亮进入网页版 cloud1 的 roomService“上传代码”页，随后反馈“部署成功”。再次从微信模拟器调用 whoami，实际返回如下信息，确认新版开赛后端已生效：

```json
{
  "ok": true,
  "stage": "p4-room-start",
  "capabilities": {
    "start": true,
    "cancelStart": true,
    "submitAnswer": false,
    "finish": false
  },
  "identified": true,
  "environmentId": "cloud1-d6gvp9cql29a1164e"
}
```

以上是云端响应的脱敏摘要，identified 是本地检查账号标识存在后得到的布尔值。它证明新版入口和身份调用可用，不代替双账号真实开赛、取消、同题或并发测试。该次验证未创建或关闭任何测试房间。

此前错误发生在开发者工具的自动部署接口，网页版手动上传已完成本次部署。现有证据不足以断言自动接口失败的根因是账号权限、代码或登录过期；没有为解决该错误修改 AppID、集合权限或索取密钥。
