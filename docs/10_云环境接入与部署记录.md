## 2. 代码接入

`miniapp/config/cloud.js` 集中维护环境名称与环境 ID。`createRoomClient({wxApi:wx})` 默认连接该环境；显式传入 envId 时按传入值连接，未确认请求仍按环境隔离保存。

开发联调页初次打开默认填写 cloud1。如果此前手动使用过别的环境，页面会保留本机保存的选择，应核对后切回 cloud1。配置环境 ID 不会自动发起调用；普通设置、答题占位页仍可独立打开。

环境 ID 不是 AppSecret。本次没有把 AppSecret、访问令牌或账号密码写入仓库。

## 3. 部署中处理的问题

首次上传时，平台先创建函数，随后因函数仍处于 Creating 状态而拒绝更新代码。确认函数转为 Active 后，使用同样的目标环境和函数名重试，得到 success=true；没有创建第二个函数或另一个环境。

微信 CLI 默认创建 Nodejs16.13，原 package.json 将最低版本写为 ≥18。核对当前依赖并使用开发者工具自带 Node.js v16.13.1，实际通过 SDK 入口加载、无身份拒绝、创建／重复请求／加入／房满／准备／退出的本地检查后，将最低版本修正为 ≥16.13，再完成部署。测试夹具使用的 structuredClone 在本次 Node 16 检查中由 v8 序列化替代，生产代码不依赖该测试函数。完整 66 项自动测试使用 Node.js v24.22.1。

这是基于实际运行环境的技术约束修正，未变更房间业务规则。正式发布前仍需评估平台推荐的运行时、依赖和超时配置，并做真实负载与冷启动测试。

## 4. 联调页缺失与真实调用修复

最初 miniprogram-automator 0.13.0 只能读取工具版本 `2.01.2510290` 与基础库 `3.17.5`，页面执行没有按时返回。之后组长报告 `./pages/backend-check/backend-check.wxml not found`。检查实际配置发现，“后端联调”模式被添加在旧的 `software-engineering-project-initiation/miniapp` 中，该副本没有新增页面；完整页面位于 `software-engineering-project-backend/miniapp`。

已打开正确项目，为本机项目添加“口算小搭档-后端联调”的名称，并在共享配置中预置“后端联调”编译模式。旧项目的文件和设置保留。切换后实际页面查询和代码执行恢复。

随后真实云调用返回 `INVALID_ARGUMENT`，进一步定位到平台自动附加的 `tcbContext` 被字段白名单拒绝。现只忽略 `userInfo`、`tcbContext` 两个传输元数据字段；身份、环境和房间归属仍由可信 `getWXContext()` 决定，其他未知业务字段仍拒绝。增加了伪造元数据不能影响身份、环境和房间归属的用例，并改进参数错误信息：只显示受限字段名，不回显任何字段值。

修复重新部署后，实际身份查询返回 ok=true、apiVersion=1，环境及 AppID 均匹配。随后 6 项数据库客户端读写权限检查和 7 项单账号房间流程检查通过。测试房间已由房主退出并关闭；原始 OPENID 和完整用户标识未写入公开记录。
