# 小学口算练习微信小程序——项目实施计划与分工

版本：v0.4｜更新日期：2026-10-30｜状态：设置、房间草图与重连修复已随 PR #1／#2 合并。P2 后端基础代码、本地测试与联调入口在开发分支完成；已确认 cloud1 环境并部署 roomService，真实双账号验证待完成，核心练习与完整比赛仍未完成。分工认领和日期待补充。

## 1. 本轮调整与实施思路

组长反馈已经与老师讨论，老师建议增加限时功能及两个学生同时在线比赛答题。本计划据此调整，反馈来源和规则提案见[教师反馈与需求变更记录](06_教师反馈与需求变更记录.md)。两项功能已纳入计划，本文没有将暂定参数写成教师已确认的要求。

2026-10-27 组长确认加入混合运算、小数和分数，并沿用闫心如草图的开始规则。按[扩展题型与开赛规则确认](07_扩展题型与开赛规则确认.md)落实：先做整数两步无括号混合、一位小数加减、同分母分数加减；双方准备后由房主开始、倒计时 3 秒，取消开始后留在原房间并清除双方准备。题型年级依据仍待核对，不能将确认范围记为功能完成。

需求以[立项稿 v0.5](01_项目立项与NABCD草稿.md)为准：保留 FR01—FR07，新增 FR08 限时练习、FR09 双人房间、FR10 同步答题与统一判分、FR11 在线同步与恢复；新增 AC07—AC10，公开试用 AC06 扩展为验证双人比赛。

总体顺序：**确认普通／限时／双人三种流程 → 原型及双端后端可行性验证 → 单人完整流程与限时 → 复习功能和双人在线比赛 → 集中测试 → 正式发布与交付**。

原“仅本机、不设后端”的约束调整为：单人记录继续本地保存，比赛增加可信身份、房间后端、服务端计时和判分、云端比赛记录。候选后端为微信云开发，实际环境、SDK、权限和成本先验证。个人历史跨设备同步、随机匹配、多人赛、聊天、公开排行榜、拍照识别和班级管理仍不在首版范围。

本阶段仍不安排家长访谈。题型资料、教师后续意见及原型试用按[需求调研与验证计划](02_需求调研与验证计划.md)记录。出题与批改使用确定的数学算法；AI 辅助开发，负责成员需要理解、检查和解释自己的实现。

## 3. P1：明确新范围、规则与责任

**目标：**把教师的两项建议转成能实现、能检查的需求，并识别新增依赖。

主要工作：

1. 记录两项教师反馈及来源，确认仍保留普通单人练习；将细化方案与教师原话区分，补充实际讨论信息。
2. 记录已确认的扩展题型范围，补充教材依据；落实整数、小数、分数的输入、精确判题与保存要求。评审尚未确认的限时时长及其他参数，已由 S10 确认的开始交互不重复列为待决定。
3. 评审双人房间码、两个独立身份、准备与开赛、同题同限时、按正确题数计分、平局、提前交卷、退出和断线行为。详细默认值集中在变更记录中维护。
4. 核对小程序及后端账号、云环境、权限、额度与成本，明确发布依赖；规划至少两个独立微信账号和两部真机的测试条件，不收集账号密码到仓库。
5. 调整分工和时间，明确房间、裁判、同步、界面各自的负责人；确认接口与数据负责人后再分解任务。

建议分工：袁嘉亮负责反馈、范围、后端环境和房间权限方案；闫心如整理题型与交互场景；何顺整理计时、判分与截止规则；彭方鑫整理同步、恢复、数据保存及双端测试场景。

交付物：新增需求和变更记录、规则表、后端与发布依赖清单、建议分工和任务计划。

完成条件：新旧模式无规则冲突；参数和资源有明确决定或待确认安排；分工有实际认领记录。仅记录教师意见不等于本阶段全部完成。

2026-10-30 进度：袁嘉亮的第一阶段已形成身份、创建／加入／查询／准备／退出房间及请求恢复代码，配套[接口交付](08_组长后端第一阶段交付与接口.md)与[部署验证指南](09_云开发部署与双账号验证.md)。本地检查通过，roomService 已部署到 cloud1；组长反馈已创建集合并设置权限。真实双账号验证仍待完成，因此 P2 不标完成。闫心如可开始接正式房间页面，何顺继续单人题目与判题，彭方鑫继续结果／本地记录及恢复适配；均不必等待完整比赛后端。

主要工作：

1. 在设置、答题、结果、订正、历史页面基础上增加模式与时长选择、创建／加入房间、准备状态、同步倒计时、比赛中状态及对局结果；补充房满、房间失效、断网和等待结算提示。

3. 候选云开发方案先做最小验证：两个独立微信身份调用后端，读取服务端时间和同一房间状态；写入后可再次读取；非参与者访问被拒绝；记录 SDK、环境模式、权限与实际结果。

5. 约定客户端／后端接口及错误：身份失败、房满、房间过期、未开赛、已经交卷、答案已锁定、超过截止、请求重复、服务暂不可用等。
6. 建立页面、共享数学规则、本地存储、房间服务、裁判服务和同步适配层的项目结构；示例数据与真实联网演示明确区分。

## 5. P3：实现单人完整流程及限时练习

**目标：**先有可运行的普通与限时练习，为比赛复用题型和页面。

主要工作：

1. 实现配置检查、加减法出题、标准答案与去重；合法题不足时明确提示，不更改范围或无限等待。
2. 实现答案输入、提交前修改、进度、漏答确认和结果展示，空白与数值 0 分开，重复提交只记录一次。
3. 加入限时开关及所选时长；题目准备后点击开始才设截止时间；显示倒计时，时间到锁定输入并自动批改，无需漏答确认。
4. 保存模式和截止时间，切后台或退出不重置计时；超时重入直接结算已保存答案。手动交卷与超时回调同时触发时只生成一份结果。
5. 抽离可复用的数学规则、计时和结果展示逻辑。单人依本机计时，后续比赛必须切换到服务端起止时间和服务端判定，不能直接相信本机分数。
6. 完成普通／限时的正常及边界自测，记录保存失败和未确认参数。

建议分工：闫心如实现设置、时长及倒计时界面；何顺实现题目、答题、批改和截止逻辑；彭方鑫实现草稿、结果与模式存储；袁嘉亮负责集成、接口检查和问题跟踪。

交付物：单人普通／限时的加减法版本、计时与提交边界自测、手机演示。

完成条件：普通流程仍可使用，限时到期自动结算、后台计时和恢复正确；不重复保存。此阶段尚不等于双人比赛或全部运算类型已完成。

## 6. P4：完善复习功能并实现双人在线比赛

**目标：**复用本地规则和页面，完成两部设备之间的真实房间、答题和统一结果。

### P4.1 完整题型、精确判题、订正和历史

在 P3 加减法基础上，补充乘法、整除、整数两步混合、一位小数加减和同分母分数加减，共覆盖设置目录的 13 个预设。按 ruleId 生成，检查题库容量：例如表内乘法交换算重复时仅 45 题，选择 50 题应提示调整。混合运算按优先级计算；小数用十分之一整数计算；分数用整数对判等，接受等值分数而不强制约分。补齐小数点、分子／分母输入及非法格式提示，区分 0 与未答。

实现原题订正和本人历史，保存 ruleId、规则版本、结构化原题、精确答案和用户原输入，旧记录不依赖新规则重算。普通、限时、比赛及订正记录区分模式并去重，本人比赛逐题结果仅在比赛整体结束后取得。已完成比赛的错题可发起本地订正；保留上限和云端到期行为按变更记录执行。个人历史跨设备同步仍不加入。

何顺负责规则扩展，彭方鑫负责结果、订正及存储，闫心如完善界面，袁嘉亮协调集成。

### P4.2 房间与同时开赛

袁嘉亮实现可信身份、创建和加入房间、服务端生成房间码、两个席位的原子占位、准备状态、房间失效及访问权限。双方准备后由房主发起开始；何顺提供服务端同题生成和容量检查，袁嘉亮原子建立 attemptId，并在题目准备完成后设置 3 秒后的统一起点。取消开始在服务端检查尚未开赛，保留房间配置和两人、清除准备；重新开始产生新 attemptId。闫心如实现房主／加入者不同按钮及取消交互，彭方鑫接入状态查询、批次切换和校时。

以两个独立微信身份和两部设备演示双方进入同一局，第三人无法加入，同一身份不能占两个席位；取消或过期房间不能开赛。

### P4.3 比赛作答、判分和异常恢复

何顺实现所有已纳入题型的服务端精确判题、答题锁定、截止校验、去重和唯一结算，联调提前交卷和同分平局；答案请求检查 roomId 与 attemptId，已取消批次不能影响新局。客户端不发送可信分数，比赛结束前不公开标准答案或逐题判定。

彭方鑫实现前台状态轮询、操作后刷新、未确认请求提示、稳定请求编号重试、后台暂停轮询和重连恢复；读到服务端最终结果后再更新本地历史。网络故障不延长比赛，也不在客户端擅自判胜负；恢复以服务端成员、准备和当前批次为准，不默认回到单人等待，不复活已取消的倒计时。

袁嘉亮复查每个在线接口的身份、成员及状态检查，确保客户端不能直接改写房间和分数。闫心如完善等待对方、断线、超时、结束及重试界面。服务端按需检查截止并幂等结算，清理任务处理到期数据，不依赖手机在线维持结果。

交付物：普通／限时练习、13 个题型预设及精确判题、订正历史、双人在线比赛可运行版本、房间与裁判接口、双端联调和异常记录。

完成条件：FR01—FR06、FR08—FR11 有可演示实现；两端题目和配置一致，读取同一结果，断线重连不延时或重复计分。FR07 额外动画／音效仍暂缓。

## 7. P5：计时、联网与正确性集中测试

**目标：**覆盖本地基础功能和新增在线故障，不能仅看两台设备正常答题一次。

主要工作：

1. 回归原 AC01—AC05，独立核算各题型的边界与累计生成题，特别覆盖混合运算优先级、1 与 1.0、2/4 与 1/2、零分母和合法题不足，检查普通练习、订正、保存和页面交互。AC03 的本机速度目标与在线同步目标分别统计。
2. 按 AC07 验证三档时限、截止边界、后台继续计时、超时重入、手动和超时同时交卷；检查只保存一次。
3. 按 AC08 用两个独立身份检查同题同限时、房主启动与 3 秒倒计时、取消留房并清除准备、重新准备和新批次、分数与平局、提前交卷后等候、比赛结束前不泄露答案。
4. 按 AC09 检查开始／取消边界竞争、重复开始、旧批次迟到请求、准备或倒计时断线恢复，以及并发加入、第三人、重复身份、非参与者访问、伪造分数／时间、重复答案、迟到请求、断线重连、服务重试、取消及过期房间、结果去重和到期访问。

6. 使用测试时钟或测试环境覆盖截止前、恰好截止和截止后；生产环境不能提供用户可操控的裁判时间。记录断网前已确认和未确认答案的差异。
7. 缺陷记录复现步骤、预期／实际结果、负责人、修复提交和复查结果；修复联网功能后回归普通练习。

建议分工：彭方鑫牵头测试与问题汇总；何顺验证数学、计时和判分；袁嘉亮验证并发、接口权限与部署；闫心如验证双端界面及可理解性。各人自测后交叉检查。

交付物：AC01—AC05、AC07—AC10 的实际结果、双端真机和异常记录、缺陷修复证据、资源消耗观察。

完成条件：新增高优先级需求均有对应测试，影响核心使用的问题解决，剩余限制如实说明。全部指标均是待执行目标，不预填通过；公开访问 AC06 留到 P6。

## 8. P6：小程序和后端发布、双人公开验证

**目标：**普通用户能使用限时练习，并由两个独立账号完成一场在线比赛。

主要工作：

1. 复查平台账号、类目、后端环境、权限、费用及提交发布事项；区分测试与正式环境，核对客户端所连接的后端及规则版本。
2. 发布配套后端、数据访问策略与清理任务，再按平台流程提交和发布小程序。后端部署成功不代表小程序审核通过，两者均需记录。
3. 执行扩展后的 AC06：两个未加入开发或体验名单的普通用户账号完成创建／加入、准备、答题、结算，并验证单人限时练习。保存版本、入口与实际访问结果。
4. 更新正式入口和使用说明，说明普通／限时／比赛的区别、网络要求、计分、到期及本地／云端数据边界。
5. 整理教师反馈、需求变更、实现与测试、资源依赖、项目限制和成员实际贡献，准备课程报告和演示；公开试用发现问题后修复复查。

建议分工：袁嘉亮负责后端发布、整体交付和汇报；彭方鑫协助小程序发布、清理验证和普通用户双端测试；闫心如整理操作说明及原型；何顺整理计时、裁判与规则证据。全员核对各自贡献。

交付物：正式小程序入口和配套后端版本、AC06 双人公开试用记录、使用说明、项目报告及贡献材料。

完成条件：两个普通用户通过正式入口完成比赛，单人限时流程可用，前后端版本一致且结果有证据；“提交审核”或团队内部体验不能标成已公开交付。
