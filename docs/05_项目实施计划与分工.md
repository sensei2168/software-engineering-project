# 小学口算练习微信小程序——项目实施计划与分工

版本：v0.1｜日期：2026-10-16｜状态：实施计划草案，具体分工、起止日期及任务认领待组内确认。

## 1. 计划依据与实施思路

本计划由组长与 AI 讨论形成的六阶段汇报方案整理，按组长要求加入项目仓库。需求范围以[项目立项与 NABCD 分析](01_项目立项与NABCD草稿.md)中的 FR01—FR07、验收目标 AC01—AC06 为准；本文细化实现顺序，不新增已确认的用户需求，也不表示已经完成开发或测试。

总体顺序：**明确规则 → 原型和模块约定 → 加减法完整流程 → 乘除法与复习记录 → 集中测试 → 正式发布与课程交付**。

首版采用微信小程序形式，先支持本设备使用，暂不建设复杂账号、云同步、拍照识别、语音识别或班级管理。出题和批改按确定的数学规则计算；AI 辅助理解技术、编写和检查代码，不作为运行时标准答案的必要来源。

本阶段不安排家长访谈。需求依据和验证按[需求调研与验证计划](02_需求调研与验证计划.md)执行；教材资料、教师意见、同类工具分析和同学试用分别记录，不混同为真实家庭验证。

立项稿的 M1—M6 按课程过程划分；下表的 P1—P6 按实现工作划分。二者编号分别保留，避免把“集中测试”与“正式发布”混在同一个完成状态中。测试贯穿开发，P5 是集中验证阶段；发布条件从 P1 就开始核对。

| 实施阶段 | 本阶段重点 | 对应立项阶段 | 完成后可展示的成果 | 计划起止日期 |
|---|---|---|---|---|
| P1 需求与规则 | 明确范围、规则、分工和发布前提 | M1、M2 | 需求清单、规则表、初步任务与发布条件记录 | 待补充 |
| P2 原型与模块约定 | 明确页面、跳转及各模块输入输出 | M2 | 可演示原型、页面与数据流说明、项目基本结构 | 待补充 |
| P3 加减法最小完整版本 | 完成设置、出题、答题、批改和基本恢复 | M3 | 手机上可完成一次加减法练习 | 待补充 |
| P4 首版功能完善 | 加入乘法、整除、订正和历史 | M4 | FR01—FR06 对应功能可连贯使用 | 待补充 |
| P5 集中测试与修复 | 核对数学、异常、真机表现和操作流程 | M5 的测试部分 | 测试记录、缺陷修复与复查证据 | 待补充 |
| P6 发布与交付 | 正式发布、普通用户验证和报告整理 | M5 的发布部分、M6 | 正式入口、使用说明、访问验证及项目报告 | 待补充 |

## 3. P1：明确需求和出题规则

**目标：**先说清楚做哪些功能、每项功能如何判断正确，再进入实现。

主要工作：

1. 确定完整使用流程：家长设置练习，孩子作答，提交后查看结果，再订正或查看历史。在线作答仍是当前方案，是否需要纸质导出应在评审中确认。
2. 确认首版规则：题量默认 30 道及允许调整的范围；加减法的操作数与结果范围；是否进退位；减法结果非负；除法先做整除且除数非零。依据教材资料整理规则，不直接把设计假设标为年级标准。
3. 明确异常行为：漏答怎样统计、非法输入怎样提示、重复提交怎样处理、合法题目不足时如何提示、退出后是否继续练习，以及保存失败如何说明。
4. 核对实际小程序账号和适用的发布条件，记录缺项、准备工作及负责人，避免把这项工作拖到编码完成之后。
5. 评审范围和建议分工，补充成员 GitHub 用户名与截止日期，再将工作分解为可认领的任务。

建议分工：袁嘉亮汇总需求、主持范围和任务评审；闫心如整理题型资料；何顺检查规则是否能实现和测试；彭方鑫参与存储、异常及发布条件讨论。

交付物：编号化需求清单、题型规则表、正常和异常行为说明、账号与发布条件检查记录、初步任务分配。

完成条件：核心规则有明确表述；未确认项有记录及处理安排；成员能够解释自己的拟负责范围。缺少真实确认时不将其标为已通过评审。

## 4. P2：制作原型并约定模块配合方式

**目标：**先检查页面和操作流程，再约定各模块传递什么数据。

主要工作：

1. 制作练习设置、答题、结果、错题订正和历史记录五类页面，补充无历史、无错题、存在未完成练习和保存失败等状态。
2. 用同一组示例题走完整个原型，检查开始练习、返回修改、漏答确认、提交、订正和查看历史等跳转是否完整。
3. 明确页面职责和数据流，至少形成下面的输入输出约定。正式接口与字段约束在后续设计文档中细化。
4. 建立小程序项目基本结构，区分页面、出题批改规则和存储模块，确认成员能运行基本页面；尚未完成的功能可用明确标注的示例数据演示。
5. 组织原型评审，按调研计划安排同学试用，记录问题并修改。原型模拟成功不等于真实计算、存储或性能通过验证。

| 部分 | 输入 | 输出或处理结果 |
|---|---|---|
| 练习设置 | 用户选择的类型、范围、题量 | 经过检查的练习配置 |
| 出题规则 | 练习配置 | 带编号的题目及标准答案，或不能生成的原因 |
| 答题页面 | 题目、已保存的用户答案 | 与题目编号对应的答案；空白单独表示 |
| 批改规则 | 题目、标准答案、用户答案 | 每题正确／错误／未答状态及汇总统计 |
| 记录存储 | 未完成练习或已提交结果 | 保存／读取结果或明确的失败原因 |

建议分工：闫心如牵头原型与设置页面；袁嘉亮协调页面和模块约定；何顺核对出题与批改所需数据；彭方鑫核对结果、历史和存储所需数据。

交付物：原型及其访问方式或截图、页面跳转说明、模块输入输出约定、可运行的基本项目、原型问题记录。

完成条件：可以通过原型演示一次完整练习；各成员知道自己模块的输入、输出和异常；核心操作不存在无去向的按钮或页面。

## 5. P3：实现加减法最小完整版本

**目标：**手机上能从设置开始，完成一组加减法练习并得到正确批改结果。

主要工作：

1. 实现设置页面，检查必填项、题量和受支持的范围，对空值及越界值给出提示。
2. 实现加减法出题，计算标准答案，检查题目范围和单轮去重。若合法题目不足，提示减少题量或调整配置，不无限等待或擅自更改规则。
3. 实现答题页面，显示题目、答案输入和进度，允许提交前返回修改。未作答与输入数值 0 必须区分。
4. 实现提交和批改，按题目编号对照答案，显示正确、错误、未答数量及逐题结果。漏答时先确认，重复提交只形成一次结果。
5. 接入未完成练习的基本保存与继续功能；读取或保存失败时提示实际情况。P3 先完成草稿恢复，已提交历史列表及其管理在 P4 完善。
6. 集成页面和规则模块，用预先核算的样例检查正常流程和关键异常，每次修改同时完成本模块自测。

建议分工：闫心如负责设置页面；何顺负责出题、答题和批改逻辑；彭方鑫负责结果展示和基础存储；袁嘉亮负责协调集成、核对模块约定和跟踪问题。

交付物：可运行的加减法版本、核心规则自测记录、一次完整流程演示、已知问题清单。

完成条件：合法配置能够生成练习；正确、错误和空白答案判定符合规则；重复提交不重复生成结果；成功保存的未完成练习可以继续。此时仅完成首版的一部分，不宣称 FR02 的全部运算类型已实现。

## 6. P4：补充乘除法、订正和历史记录

**目标：**在稳定的基本流程上完成首版约定的功能，复用已有页面和批改流程。

主要工作：

1. 补充整数乘法和整除规则，核对操作数、结果范围、除数非零和整除条件；扩展规则模块，复用设置、答题和结果页面。
2. 实现订正功能：将所选练习的错误及未答原题组成新练习，保存独立结果，不覆盖原练习。订正题量可以少于新建练习的最低题量；没有可订正题时解释原因。
3. 实现本设备历史记录，展示日期、题量、正确数和逐题结果。保留数量、超限清理及订正关联按立项规则执行；重新进入后能查看已成功保存的数据。
4. 实现历史清除确认，避免误删正在进行的练习；完善未完成练习的继续／放弃选择，并说明本地存储的限制。
5. 完善异常反馈及界面说明，例如无历史、没有错题、存储读取失败、写入失败及不支持的配置，不显示虚假的保存成功。
6. 联调四类运算和复习流程，检查增加新题型后是否影响已完成的加减法功能。

建议分工：何顺扩展运算规则及规则测试；彭方鑫完成订正、历史与存储；闫心如完善页面交互；袁嘉亮协调集成与范围控制。各模块负责人同时负责本模块异常处理和自测。

交付物：首版功能可运行版本、题型配置及依据、订正和历史演示、模块自测与联调记录。

完成条件：FR01—FR06 均有可演示实现，设置、四类题型、答题、批改、订正和历史能够连贯使用；FR07 额外音效或动画仍暂缓，不因进入完善阶段自动加入范围。

## 7. P5：集中测试和修复问题

**目标：**用可核对的结果检查正确性、异常处理、操作流程和真机表现。

主要工作：

1. 数学与规则测试：核对各模板的正常和边界情况，包括结果为 0、进退位、整除条件等。使用独立参考计算或人工核算，不把生成器自身答案作为唯一正确性依据。
2. 功能和异常测试：覆盖全对、全错、空白、非法输入、重复提交、题目不足、订正、历史清除、中途退出、读取失败和写入失败。
3. 真机检查：记录手机型号、系统、微信版本和小程序构建版本，检查页面是否完整、输入是否方便、提示是否清楚，以及题目生成和批改耗时。
4. 操作流程试用：按调研计划邀请同学完成指定任务，记录耗时、求助、误操作和实际反馈。该结果仅支持早期流程评价，不代表家长或儿童认可。
5. 问题闭环：在 GitHub 记录复现步骤、预期与实际结果、负责人、修复提交和复查结果；修复后检查受影响的原有功能。

验收以立项稿 AC01—AC05 为准，不在本计划降低指标：例如每个规则模板累计至少核对 1,000 道生成题、30 题生成和批改各进行 20 次计时、完成 10 组中断恢复检查，以及至少 3 名同学的首次操作任务。以上均是目标，尚无实测成绩。

建议分工：各成员先自测，再交叉检查；彭方鑫汇总测试和缺陷记录；何顺重点排查数学与批改问题；闫心如修改交互问题；袁嘉亮跟踪问题及整体完成情况。

交付物：测试用例与实际结果、真机记录、试用记录、缺陷清单及修复复查证据。

完成条件：AC01—AC05 有实际检查结果；影响核心使用的问题已解决，剩余限制有明确说明。AC06 的普通用户公开访问验证留到 P6 完成，不能提前标为通过。

## 8. P6：正式发布与整理交付材料

**目标：**让普通用户实际试用，并形成可检查的课程交付。

主要工作：

1. 复查 P1 开始记录的账号与发布准备事项，根据实际平台要求处理提交、审核、修改和正式发布，记录状态及版本，不预填审核通过时间。
2. 更新 README 的正式访问入口、小程序名称、版本及使用说明，确保介绍的功能与发布版本一致。
3. 按 AC06 请至少 1 名未加入开发或体验名单的普通用户，从正式入口完成设置、答题和查看结果，记录实际操作结果。内部演示不能替代这一项。
4. 整理需求、设计、实现、测试、问题处理及项目限制；收集每位成员的实际任务和修改证据，由成员撰写自己的工作说明与体会。
5. 准备课程演示、项目报告和资料导航，核对文档与最终版本一致；试用发现影响使用的问题时修复并重新验证。

建议分工：袁嘉亮统筹交付和汇报；彭方鑫协助发布准备及访问验证；闫心如补充原型、页面和使用说明；何顺补充规则、核心实现与测试说明。全员核对各自贡献。

交付物：正式小程序入口、发布记录、普通用户验证记录、使用说明、完整报告及贡献材料。

完成条件：公开入口和核心流程实测可用，AC06 有证据，课程材料可访问。若发布受阻，记录实际原因和后续动作，不将“已提交审核”写成“已经上线”。

## 9. 建议分工与任务管理

成员姓名和袁嘉亮的组长身份已确认；下表仍为待组内确认的分工建议，不是已完成贡献记录。

| 成员 | 主要职责 | 贯穿阶段的责任 |
|---|---|---|
| 袁嘉亮 | 需求、计划、协调集成、交付汇报 | 组织评审、跟踪任务与依赖、记录变更、核对整体进度 |
| 闫心如 | 题型资料、原型、设置页面及交互完善 | 保留来源与原型记录，对负责页面自测，参与交叉检查 |
| 何顺 | 出题批改规则、答题流程与异常处理 | 核对数学正确性，维护规则及边界测试，解释核心逻辑 |
| 彭方鑫 | 结果、订正与历史、存储、测试汇总和发布协助 | 检查数据保存与恢复，汇总问题证据，协助验证公开访问 |

各阶段确认后再创建或调整对应 Issues；每项任务至少填写需求或阶段编号、实际负责人、预计起止日期、依赖、完成条件及交付证据。较大的任务再拆分，后续按教案形成不少于 30 项有意义的任务及甘特图。本文是阶段实施计划，**尚未创建这些线上任务，也不是已排定日期的甘特图**。

任务完成需要文档、原型、代码或测试证据，不能只修改状态。AI 辅助产生的内容由负责成员检查、运行和解释，实际修改与问题处理保留到仓库历史中。
