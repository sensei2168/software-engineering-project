# 自动清理配置与验收

日期：2026-11-04。三个集合单条真实删除均取得组长返回：room_p2_codes 468毫秒、room_p2_requests 323毫秒、room_p2_rooms 253毫秒，均ok=true、removed=1、batchLimit=1、stoppedForBudget=false。证据见docs/evidence下对应maintenance-delete文件。

这些耗时为函数内部测量，不包含平台完整冷启动；mayHaveMore=true表示取满批量上限，不表示已经清空积压。手动执行通过不等于定时执行已通过。

## 配置步骤

1. cloud1→云函数→现有roomMaintenance，确认当前部署仍为单条删除验证版，客户端调用禁止、3秒、256MB，不开启HTTP访问。
2. 找到定时触发器配置。名称必须为room-cleanup，类型timer（定时触发），Cron填`0 */5 * * * * *`，每5分钟执行一次。若界面要求JSON配置，使用deployment/roomMaintenance-timer.config.json的内容。
3. 保存或启用；若已有同名触发器，核对并修改，不重复创建。保留当前函数代码和权限。
4. 按平台显示的下一个触发时点观察至少3次调用；理想情况下15分钟覆盖三个集合。确认真正来自定时触发，且ok=true、mode=delete、batchLimit=1。removed可为0（无候选、已续期或预算停止），须结合返回判断。
5. 若控制台没有可用执行记录，保留触发器状态并另行确认实际调用证据，不能仅凭已保存就填写“自动执行通过”。若出现付费开通提示，不升级，先反馈具体界面。

官方依据：[CloudBase定时触发器](https://docs.cloudbase.net/cloud-function/timer-trigger)。七段依次为秒、分、时、日、月、星期、年；源码上传和触发器部署是两步。仓库云函数config.json仍为空触发器，默认settings.json仍为preview；当前云端单条delete配置通过部署配置文件单独选择。以后重新部署源码时需明确保留已选运行模式；不能把preview误认为实际删除。

## 容量与回退

当前按服务端分钟数模3选集合；每5分钟的名义顺序会轮转三个集合。定时延迟可能改变选择，必须观察实际targetCollection。不要沿用每小时整点调度，否则会反复选同一个集合。

每次最多1条：理想无故障情况下共12次/小时、每个集合最多4条/小时（96条/天）。这是先验证自动链路的保守配置，尚未证明能跟上真实新增量。超过此速度的到期数据会积压，不能承诺到期后15分钟内物理删除；roomService的逻辑访问期限仍独立生效。需要根据积压与资源用量再调整频率或批量，不直接扩大到未经3秒限制实测的批量。

运行异常先停用room-cleanup触发器，保留证据；如需回退只读，部署预览包。停止调度不会影响比赛判分。已经删除的到期数据不会因回退恢复。
