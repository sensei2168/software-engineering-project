# GitHub 项目记录使用说明

版本：v0.3｜更新日期：2026-10-16｜适用于“小学口算练习微信小程序”。

仓库：[sensei2168/software-engineering-project](https://github.com/sensei2168/software-engineering-project)。本轮修订前已读取 main 分支 80db3e4，确认 README、4 份初步文档和任务模板已上传。本版新增需求调研与验证计划，旧访谈提纲保留为历史材料。具体更新与合并状态以仓库提交历史为准。

## 1. 各区域记录什么

| 区域 | 内容 | 组长检查要点 |
|---|---|---|
| README | 简介、成员、状态、文档与试用入口 | 姓名是否真实，建议分工是否已经确认，状态是否与证据一致 |
| docs | 立项、调研、会议、需求、设计、测试与协作记录 | 来源、日期、版本、待核实项是否清楚 |
| Wiki（若已启用） | 过程导航、阶段说明及关键决策 | 链接到 docs 正文，避免维护相互矛盾的两套内容 |
| Issues | 任务与进展 | 负责人、期限、依赖、完成条件和结果证据 |
| Pull requests | 修改与评审 | 解决哪个任务、改了哪些内容、如何检查 |

课程要求的会议时间、实际参会者与角色、照片、思维导图和 NABCD 仍须按真实过程补齐。当前立项文档中的讨论导图不是实际会议证明。

## 3. 当前材料如何维护

1. 更新已有文件前，先阅读 GitHub 当前版本，保留其他成员新增的内容。
2. 修改范围或规则时，同时核对立项文档的 FR 编号、README 和相关任务；在立项变更表中写清原因和影响。
3. 小组协作可采用“建立任务—在分支修改—提交 Pull request—组员审阅—合并”的过程；小范围文档修订若直接提交，也应留下清楚的提交说明。
4. 教师意见、资料来源和试用记录产生后，再填写真实日期、参与者、结论及证据链接。
5. 文件上传或合并完成后，检查正文、表格、导图和内部链接是否正常显示。

使用网页上传时，上传仓库中的 README 和 docs，保留目录结构，不上传本地 .git。已有 .github/ISSUE_TEMPLATE/task.md 无需重复创建。若以后新增隐藏目录中的文件遇到 This file is hidden，可用 Add file → Create new file，直接输入包含 .github/ 的完整文件路径，并粘贴包含配置头的完整文本。

操作参考：[GitHub 上传文件](https://docs.github.com/en/repositories/working-with-files/managing-files/adding-a-file-to-a-repository)、[创建文件](https://docs.github.com/en/repositories/working-with-files/managing-files/creating-new-files)、[Issue 模板](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/about-issue-and-pull-request-templates)。

## 4. Wiki 导航建议

如果仓库已启用 Wiki，可建立“小学口算练习微信小程序项目记录”首页，链接到 README、立项稿、当前调研计划、会议、任务计划、原型及测试材料。暂未产生的材料写“待补充”，不用空链接伪装成已完成。

Wiki 的可用性与仓库及账号情况有关，按当前仓库设置核对；正文仍保存在 docs。参考：[GitHub 关于 Wiki](https://docs.github.com/en/communities/documenting-your-project-with-wikis/about-wikis)。

## 5. 首批 Issues 建议

以下对应立项稿 T01—T08；本表是待创建或待核对的任务清单，不代表线上已有这些 Issues。负责人先按建议分工讨论，确认后认领，日期按课程实际期限安排。

| 任务 | 完成条件 |
|---|---|
| T01 组织立项讨论并补充成员信息 | 保存真实时间、参与者、分工、决策、照片和讨论结果 |
| T02 建立题型规则资料表 | 每条规则有出处、例题、适用限制和待确认项 |
| T03 分析同类工具核心流程 | 至少 2 个工具有可追溯记录，区分官方介绍和亲自试用 |
| T04 记录教师意见并评审范围 | 写明真实意见、决定、理由及影响需求；未反馈时保持待办 |
| T05 核对账号与公开发布条件 | 记录实际条件、缺项和办理计划，不提交账号凭据 |
| T06 明确出题及批改规则 | 定义正确、错误、空白、重复提交和候选题不足等情况 |
| T07 制作并试用原型 | 覆盖设置、答题、结果、订正和历史，保留真实操作记录 |
| T08 分解开发计划 | 按课程要求落实不少于 30 项有意义的任务、个人责任与甘特图 |

家长访谈已从当前必做任务中移除。若线上曾创建过此类任务，保留其历史，说明改用哪些验证方法，并调整任务状态；不要填写“访谈已完成”。

## 6. 组长每次检查的内容

- 任务有明确负责人、完成条件和预计时间；遇到阻碍如实记录。
- 完成任务时附文档、代码、原型或测试链接，每位成员能解释自己负责的内容。
- 建议、已确认决定与实际完成结果分开记录，不能只改复选框而缺少证据。
- 本阶段不安排家长访谈，但题型资料、教师审阅与原型检查仍需要执行和记录。
- GitHub 负责保存过程与代码；小程序是否已公开交付，要以正式入口和普通用户实际访问结果为准。
